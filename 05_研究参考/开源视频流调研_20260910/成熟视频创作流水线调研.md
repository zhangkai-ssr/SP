# D:\sp 成熟视频创作流水线调研与改造建议

调研日期：2026-09-10  
适用项目：`D:\sp` 现有 Python/FFmpeg 竖屏短视频工具链  
结论级别：基于公开项目文档、平台官方资料和本地源码快照的工程判断；没有运行第三方云服务、没有上传或发布任何视频。

## 结论先行

`D:\sp` 不需要整体改写，也不建议直接把某个“大而全”的开源项目塞进现有目录。最合适的是保留当前轻量的 JSON 分镜 + Python/FFmpeg 合成方式，选择性吸收成熟项目的五项能力：

1. **明确的分阶段流水线与人工检查点**：脚本、配音、字幕、素材、合成可以分别停止、审阅和重跑。
2. **可追溯的任务清单**：记录脚本版本、素材来源、生成参数、工具版本、产物和质检结果。
3. **素材与文案按段绑定**：避免“素材看着不错，但和当前台词没有关系”。
4. **自动质量门禁**：字幕安全区、时长、黑帧、静音、响度、分辨率、编码、缺失素材在交付前统一检查。
5. **导出可编辑的剪映草稿**：自动生成初稿后，仍能在剪映中人工微调节奏、字幕和镜头。

首选参考组合是：

- 用 **MoneyPrinterTurbo** 学任务编排、分阶段停止、素材来源记录、素材缓存和编码降级。
- 用 **NarratoAI** 学已有长视频的解说重剪、OST 分段、字幕安全区、音频处理和剪映草稿导出。
- 只在需要高规格动态图表、复杂模板或大批量参数化视觉时，再评估 **Remotion**；当前阶段不建议把 Python 渲染链整体改写为 React。
- Runway/Seedance 等生成式视频服务只作为“缺关键镜头时的素材供应商”，不应成为整条流水线的硬依赖。当前已连接的 Runway Free 工作区没有可用额度，因此近期主流程应保持离线/低成本可运行。

## 现有 D:\sp 的基础

目前已有两条可用路径：

- `make_video.py`：适合文字动画、背景图和 BGM 驱动的 1080×1920 竖屏视频。
- `存在主义项目\manju.py`：适合 JSON 分镜、图片/视频混用、TTS、字幕和 Ken Burns 运镜。

本机已有 Python 3.12、FFmpeg、Edge TTS/Pillow/imageio 等基础组件，并安装了剪映专业版。这意味着现在最缺的不是“再装一个渲染器”，而是**任务管理、素材追溯、质检和可编辑交付**。

## 成熟创作流程应该是什么样

```text
选题与证据
    ↓
标题/封面/开头钩子一起设计
    ↓
结构化脚本（每段目标、台词、画面意图、时长）
    ↓  人工检查点 A：事实、表达、节奏
配音或原声切分
    ↓
字幕时间轴与分句
    ↓  人工检查点 B：发音、断句、专有名词
逐段素材检索/生成 + 来源记录
    ↓
确定性时间线（分镜与素材一一对应）
    ↓
FFmpeg 初稿 / 剪映可编辑草稿
    ↓
自动质检（画面、声音、字幕、编码、来源）
    ↓  人工检查点 C：手机端完整观看
正式成片与交付包
    ↓
发布后复盘：开头留存、掉点、重看片段、评论反馈
```

这条流程的关键不是“全自动”，而是让自动化承担重复劳动，让人只在三处做高价值判断。YouTube 官方也把表现拆成吸引点击、持续观看和观看满意度，并强调开头几秒要兑现标题/封面的承诺；留存报告中的高点、尖峰和下坠点应反向用于下一条视频的脚本与剪辑迭代。

### MoneyPrinterTurbo：值得借鉴的真实实现

本地源码显示其完整流程位于 `app/services/task.py:1284`，顺序为：

1. 云服务密钥和 FFmpeg 预检；
2. 生成脚本；
3. 生成素材关键词；
4. 生成配音；
5. 生成/修正字幕；
6. 下载或生成素材；
7. 合成最终视频；
8. 可选发布。

其中 `stop_at=script/terms/audio/subtitle/materials/video` 是很实用的设计：昂贵步骤之前可以先看中间结果，而不是每改一句文案就整条重跑。

另外三处很适合移植：

- `app/services/task_artifacts.py:21`：使用临时文件 + 原子替换写任务 JSON，避免中断时留下半个清单。
- `app/services/material.py:86`：只记录公开且必要的素材字段，例如 provider、搜索词、素材 ID、来源页面、作者、分辨率和本地文件名。
- `app/services/task.py:637`：素材既可来自本地，也可来自 Pexels/Pixabay/Coverr 或生成式供应商；完整视频前先做依赖和凭据预检。

其 README 所述的一体化目标就是“主题/关键词 → 脚本 → 匹配素材 → 字幕/BGM → 高清短视频”。最新发布记录还增加了 Seedance、OFox/MiniMax 等生成式素材入口，说明成熟项目正在把“免费素材检索”和“按脚本生成镜头”统一成同一种素材接口，而不是让生成模型控制整条生产线。

### NarratoAI：最适合当前 Windows + 剪映环境

本地源码中 `app/services/task.py:644` 的统一重剪流程把每段标为不同 OST 类型，可分别保留解说、原声或两者；随后生成 TTS、按原片时间戳裁剪、合并字幕/配音/BGM，再输出最终视频。

最值得优先验证的是 `app/services/jianying_task.py:341` 的剪映导出：它不必先把每段视频重新编码，而是把原片、源时间戳、TTS 和字幕组织为可编辑草稿。`jianying_draft_builder.py` 会建立视频/音频/字幕轨并写入剪映草稿文件；这比只交付一个 MP4 更适合人工精修。

需注意：剪映草稿格式属于应用内部格式，可能随剪映版本变化。NarratoAI 的代码可以作为兼容性验证样本，但正式接入前应复制一份草稿目录做小样测试，不应直接批量写入现有草稿库。

### Remotion：何时才值得引入

Remotion 的优势是把视频当作 React 组件和时间线来写，适合动态图表、代码演示、品牌模板与批量变量替换。官方 AI 模板本身也是“生成脚本、图片、配音和 `timeline.json`，再由时间线同步 Elements/Text/Audio”。

但当前 `manju.py` 已经有结构化分镜和轻量动效；为了普通口播/漫剧引入 Node、React 和浏览器渲染，会增加维护面。建议只在出现以下任一需求后再做独立样板：

- 同一视觉模板需要批量生产几十到几百条视频；
- 复杂图表、代码动画、3D/粒子或精细缓动成为主要画面；
- 需要设计人员在浏览器中预览组件并复用品牌系统。

## 建议的 D:\sp 目标结构

```text
项目名/
├─ project.json              # 项目级元数据、版本、目标平台
├─ storyboard.json           # 逐段脚本和确定性时间线
├─ assets/
│  ├─ source/                # 原始素材，禁止覆盖
│  ├─ generated/             # AI 生成素材
│  └─ cache/                 # 可重建缓存
├─ audio/
│  ├─ narration/
│  └─ bgm/
├─ subtitles/
├─ work/                     # 中间产物
├─ output/                   # 正式成片
├─ jianying/                 # 可编辑草稿（实验性）
├─ material_sources.json     # 每个镜头的来源/许可/提示词/模型
├─ qa_report.json            # 自动质检结果
└─ production_notes.md       # 人工判断与交付说明
```

建议每个分镜至少包含：

```json
{
  "id": "s03",
  "narration": "这一段的台词",
  "purpose": "提出反例",
  "target_duration": 4.2,
  "visual_query": ["human checking AI output", "decision review"],
  "material": "assets/source/s03.mp4",
  "material_source_id": "src-003",
  "source_in": 12.5,
  "source_out": 16.7,
  "subtitle_safe_area": "portrait-default",
  "status": "approved"
}
```

时间线应由明确字段决定，不让渲染器临时随机挑镜头。随机化可以用于候选版本生成，但进入人工确认后必须冻结素材顺序和随机种子，才能复现同一成片。

## 分三阶段改造

### 第一阶段：低风险、高收益

不增加云服务，不改变现有视频风格：

- 为每次生成建立独立任务目录和 `project.json`。
- 把脚本、音频、字幕、素材、成片拆成可单独运行的阶段。
- 增加 `--stop-at` 或等效参数，至少支持 `script/audio/preview/final`。
- 为每个素材记录来源页面、作者、许可说明、本地文件名、下载日期；AI 素材记录模型、提示词、生成日期。
- 交付前自动检查：文件存在、时长一致、1080×1920、30 fps、H.264/AAC、无长黑帧、无长静音、响度达标、字幕不越安全区。
- 正式交付目录只保留明确命名的成片、封面、SRT、脚本、来源记录和质检报告。

建议优先级：**立即实施**。

### 第二阶段：人工可编辑与素材半自动化

- 用 Pexels/Pixabay/Coverr API 生成“候选素材池”，但最终入选需要人工确认。
- 按分镜关键词顺序下载和绑定素材，建立缓存，避免重复请求。
- 接入 Whisper 作为 Edge TTS 时间戳失败或真人配音时的字幕对齐后备。
- 单独做一个 15–30 秒的剪映草稿导出兼容性小样，再决定是否进入正式流程。
- 增加“预览版”：低分辨率、带水印、渲染快，批准后再出正式版。

建议优先级：**第一阶段稳定后实施**。

### 第三阶段：按实际需求选择

- 把 Runway、Seedance 或其他 T2V/I2V 统一封装为可选素材供应商。
- 若动态图形需求增长，做一个独立 Remotion 模板项目，不替换现有 Python 管线。
- 若需要多人或批量任务，再增加 WebUI、任务队列和断点恢复。
- 发布平台接口保持关闭；只有用户明确确认账号、文案、封面、隐私和发布时间后才单独执行。

建议优先级：**有明确业务量或镜头需求时再做**。

## 自动质检建议

每个正式成片至少通过以下门禁：

| 类别 | 检查项 | 建议规则 |
|---|---|---|
| 容器/编码 | MP4、H.264、AAC、像素格式、渐进扫描 | 与目标平台推荐保持一致 |
| 画幅 | 竖屏短视频 | 1080×1920，9:16，30 fps（除非素材有明确原因保留其他帧率） |
| 音频 | 综合响度、真峰值、静音段 | 当前短视频可继续以约 -16 LUFS 为目标；限制真峰值并报告长静音 |
| 画面 | 黑帧、冻结、缺图、拉伸 | 自动扫描，异常片段给出时间码 |
| 字幕 | 越界、过长、遮挡、断句 | 使用安全区；手机尺寸预览；专有名词人工检查 |
| 时间线 | 配音/字幕/画面尾部一致 | 偏差超过设定阈值即失败 |
| 追溯 | 素材、音乐、字体、AI 生成记录 | 缺来源时不进入正式交付目录 |

YouTube 官方推荐上传使用 MP4、H.264、AAC-LC/Opus、渐进扫描、原始帧率和 BT.709；1080p 标准帧率的参考视频码率是 8 Mbps。TikTok 官方创意资料强调 9:16 竖屏并避开界面安全区。具体平台发布前仍应重新核对当时规则。

## 发布后的成熟复盘闭环

自动化流水线只有加入数据反馈才算成熟：

1. 每条视频保存版本号和发布时间。
2. 记录标题、封面、开头版本和内容结构。
3. 发布后查看留存曲线的开头、尖峰和下坠时间码。
4. 把时间码映射回 `storyboard.json` 的分镜 ID。
5. 只改一个主要变量做下一版，例如开头表达、镜头密度或字幕样式。

不建议用“播放量高低”直接训练整条流程。先区分：用户是否点击（包装）、是否继续看（内容/节奏）、看完是否满意（价值与预期一致）。

## 风险与边界

- **版权不是“下载成功”**：保存来源页面、作者和许可说明，音乐/字体同样需要记录；不同素材站和具体资产可能有额外限制。
- **AI 生成不等于免审**：事实、肖像、商标、风格模仿和平台披露要求仍需人工判断。
- **自动发布必须独立授权**：成熟项目虽支持跨平台发布，但不应作为视频生成的默认末步骤。
- **第三方费用要在生成前确认**：云视频模型应先估算镜头数、时长、分辨率和重试成本，再创建任务；远端任务 ID 必须落盘。
- **剪映格式可能变化**：先用副本小样验证当前剪映 10.7 的读取兼容性。
- **中文路径兼容性**：现有脚本可使用中文路径，但第三方工具、字体、滤镜和命令行参数仍需在独立样板中验证；不要直接在生产目录安装重型项目。

## 推荐下一步

最合适的下一项实施工作是“第一阶段最小改造”：在不引入新云服务的前提下，为 `manju.py` 增加任务清单、分阶段预览、来源记录和统一质检；随后用一条 20 秒样片验证剪映草稿导出。这样可以马上提高可重复性与交付质量，同时保留当前已经能稳定出片的简单架构。
